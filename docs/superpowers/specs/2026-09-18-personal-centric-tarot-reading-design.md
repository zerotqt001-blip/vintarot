# Personal-Centric AI Tarot Reading

**Date:** 2026-09-18
**Status:** Proposed for implementation after user review
**Scope:** NaTarot Room reading result, provider contract, persistence compatibility, responsive behavior, and follow-up reading boundary.

## Intent

NaTarot should make the reader the subject of the interpretation. Tarot knowledge remains the reasoning and evidence layer, but the first answer must describe the reader's question, real-life dynamics, choices, reflection, and next steps before exposing card-by-card evidence.

The experience changes from:

```text
card meanings → card connections → generic guidance
```

to:

```text
question → direct answer → personal insights → reflection → action → tarot evidence
```

The change must preserve the current draw flow, spread semantics, card orientation, owner checks, V5 retrieval, provider abstraction, bilingual UI, journal save behavior, and old saved readings.

## Provider contract

The provider-facing contract will be versioned as `tarot-reading-v3`. Provider JSON keeps the existing snake_case convention; the normalized client payload uses typed camelCase fields.

```json
{
  "direct_answer": "string",
  "personal_insights": [
    { "title": "string", "body": "string" }
  ],
  "reflection_prompts": ["string"],
  "next_steps": [
    { "title": "string", "body": "string" }
  ],
  "card_evidence": [
    {
      "reading_card_id": "string",
      "position_key": "string",
      "interpretation": "string"
    }
  ],
  "deeper_reading": "string or null",
  "follow_up_suggestions": ["string"]
}
```

### Validation rules

- `direct_answer`: required, bounded, and composed as 2–4 short paragraphs. It must not begin with a card name, “the cards show”, or a spread-mechanics summary.
- `personal_insights`: 1–6 compact user-centric insight objects. Titles describe dynamics, not card names.
- `reflection_prompts`: 1–4 reading-specific questions.
- `next_steps`: 1–4 concrete actions with short titles and one explanatory sentence.
- `card_evidence`: exact one-to-one coverage of every stored `reading_card_id` and `position_key`; no provider-supplied card name, orientation, or position label is trusted.
- `deeper_reading`: nullable and optional in presentation; it is supporting synthesis, not a replacement for the direct answer.
- `follow_up_suggestions`: 0–4 context-specific suggestions, never fabricated by the client.
- All text is required to use the requested locale and remain reflective, conditional, and non-diagnostic.

The normalized `TarotReadingPayload` will include trusted metadata on each evidence item:

```ts
type TarotReadingPayload = {
  directAnswer: string;
  personalInsights: Array<{ title: string; body: string }>;
  reflectionPrompts: string[];
  nextSteps: Array<{ title: string; body: string }>;
  cardEvidence: Array<{
    readingCardId: string;
    position: TarotReadingCardContext["position"];
    card: TarotReadingCardContext["card"];
    orientation: TarotOrientation;
    interpretation: string;
  }>;
  deeperReading: string | null;
  followUpSuggestions: string[];
  disclaimer: string;
};
```

The question, category, and spread remain trusted session metadata in the route response rather than being regenerated by the provider.

## V5 prompt composition

`buildTarotReadingInput` remains the single bounded V5 context builder. It continues to include:

- question, domain, category, spread, ordered position semantics;
- exact stored cards and orientations;
- localized D1 upright/reversed evidence;
- selective V5 handbook additions;
- reversal framework, combination hints, global pattern guidance, and matching style examples.

The prompt changes only the final composition contract and guardrails:

1. Analyze the full spread before writing.
2. Start from the reader's situation and observable dynamics.
3. For relationship readings, separate feeling, intention, action, capacity, and commitment; never state another person's private thoughts as facts.
4. Treat cards as evidence for the reasoning, not as the subject of the opening answer.
5. Place card-specific interpretation only in `card_evidence`.
6. Do not expose chain-of-thought or raw retrieval text.
7. Keep money, medical, legal, and other high-stakes content reflective and non-advisory.

Provider transports continue to use the same abstraction and strict JSON mechanisms. Only the shared prompt version, schema, and provider test fixtures change.

## Persistence and compatibility

Add a nullable `reading_payload` JSON text column to `readings` through a new idempotent migration. Keep the existing columns populated for compatibility:

| Existing column | New source |
| --- | --- |
| `opening` | `directAnswer` |
| `card_readings` | normalized `cardEvidence` JSON |
| `synthesis` | compact serialized personal-insight synthesis |
| `advice` | compact serialized `nextSteps` |
| `closing` | `deeperReading` or a safe closing fallback |
| `disclaimer` | normalized disclaimer |
| `reading_payload` | complete normalized payload |

Fresh readings render from `reading_payload`. A compatibility parser will reconstruct a typed payload from legacy rows that have no `reading_payload`, using the old opening/card/synthesis/advice/closing fields and trusted session card metadata. No historical row is deleted or rewritten during migration.

The existing journal endpoint remains unchanged in shape. `saveJournal` continues to save question, notes, session, spread, context, cards, and orientations. The AI reading remains associated through `session_id`; no duplicate card database is introduced.

## Reading UI architecture

Extract the result surface from `app/room/room.tsx` into focused typed components. The exact folder may follow the repository convention, but responsibilities are fixed:

- `ReadingPanel`: owns the scroll container, loading/error states, close/save actions, and follow-up boundary.
- `ReadingHeader`: spark, localized kicker, customer question, spread context, and accessible close/save controls.
- `DirectAnswer`: renders the direct answer as short paragraphs with a constrained reading measure.
- `PersonalInsights`: compact numbered insights; no card names or large card art in this layer.
- `ReflectionPrompts`: 1–4 specific prompts that can seed the follow-up composer without changing the reading.
- `NextSteps`: numbered actions with short titles and one sentence each.
- `TarotEvidence`: native keyboard-accessible `<details>` disclosure, collapsed by default; thumbnail, trusted card name, orientation, position, and interpretation only.
- `FollowUpReading`: suggestion chips, labeled input, loading/error state, and real response rendering. It never invents a local answer when the endpoint is unavailable.

The result component receives an immutable normalized payload plus callbacks. It does not call providers, read D1, infer domains, or reconstruct card IDs.

## Desktop behavior

- Keep the Tarot table and selected cards on the left.
- Keep the reading on the right, but make it an editorial reading column rather than a tabbed report.
- The question is visible directly under the header.
- The direct answer is the visual focal point.
- Insights follow immediately in a compact numbered list.
- Reflection, actions, evidence, and follow-up follow in one scroll order.
- Prose is constrained to roughly 55–75 characters per line where practical.
- Card images appear only as small evidence thumbnails.
- Save and close remain reachable without competing with the opening answer.

## Mobile behavior

- The result surface occupies nearly the full viewport and becomes the primary task surface.
- Remove the four-tab navigation and the horizontal tab strip entirely.
- Use a single vertical scroll with question and direct answer first.
- Stack insights and actions vertically with comfortable spacing.
- Render reflection prompts as readable, touch-friendly surfaces; selecting one can seed the follow-up input.
- Use a collapsed evidence accordion.
- Keep controls at least 44px high, maintain visible focus, avoid horizontal overflow, and respect safe-area insets.
- Preserve reduced-motion behavior for panel entry and evidence disclosure.

## Follow-up boundary

Add a real `/api/tarot/follow-up` route and provider method rather than a client-side fake. The request contains `session_id`, `locale`, and the user's follow-up question. The server:

1. Re-checks owner access to the stored session.
2. Loads the historical spread and exact stored cards/orientations.
3. Loads the current normalized reading payload.
4. Sends a bounded follow-up context containing the original question, domain/spread semantics, exact drawn cards/orientations, and the current reading payload.
5. Requests a strict `{ answer: string }` response with the same safety and locale rules.

The initial V5 evidence is not re-expanded into every follow-up request. The current reading payload is the compact continuity layer. Follow-up answers are kept in client state for this session; persistent conversation history is outside this change.

## Accessibility and failure handling

- Use semantic `aside`, `header`, `section`, `h2`/`h3`, `details`/`summary`, labels, and live regions.
- Close, save, retry, accordion, chips, and follow-up controls have localized labels and visible focus states.
- `details` provides keyboard disclosure without custom tab behavior.
- Loading and provider failures remain provider-neutral and preserve the drawn cards.
- Invalid provider output remains a safe retryable error; no local generic answer is presented as AI output.
- Stale room request guards continue to invalidate interpretation and follow-up responses when the session, spread, or reading epoch changes.

## Tests and verification

Add or update tests before implementation code for:

- exact card-evidence coverage and trusted metadata injection;
- English and Vietnamese parsing/rendering;

Verification commands:

```text

```

Browser verification will cover a representative 3-card reading in English and Vietnamese at desktop, tablet, and mobile widths; evidence will remain collapsed during the primary-content check, then expand through keyboard and pointer interaction.

## Out of scope

- Changing draw, shuffle, fan, orientation, spread catalog, or card artwork behavior.
- Deleting or rewriting `lib/tarot-narrative.ts`, `lib/tarot-locales.ts`, or Guidebook behavior.
- Exposing provider secrets or raw V5 retrieval data.
- Persisting a full follow-up conversation history.
- Redesigning the broader NaTarot visual identity beyond the result surface.
